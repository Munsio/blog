# Cline Ruleset: Technical Blog Posts

## Purpose

Assist in drafting, editing, and refining blog posts. Posts must balance accessibility with precision and maintain a high standard of clarity and flow.
The Posts are representing what and why I used something, and that premise should be preserved.

## Style and Tone

- Use a friendly, professional, and confident tone.
- Avoid casual slang; maintain consistent technical language.
- Use contractions where appropriate to keep the tone natural.
- Prefer clarity over cleverness. Do not use idioms or metaphors unless they aid understanding.

## Structure and Formatting

- Use `##` for main sections and `###` for sub-sections.
- Title must clearly state the purpose of the post. Use common search terms where applicable.
- Begin with an introduction that:
  - States the goal of the tutorial.
  - Describes the expected outcome or end result.
  - Mentions prerequisites (technical skills, tools, or setups).
- Divide the body into clearly defined steps or topics.
- Use bullet points and numbered lists where appropriate.
- End with a conclusion that:
  - Summarizes what was built or achieved.
  - Suggests next steps or related topics.
  - Optionally includes a call to action (e.g. try this on your own, read another article).

## Code Blocks and Examples

- Use fenced code blocks with correct language tags.
- Precede every code block with an explanation of what the code does and why it’s needed.
- Do not assume readers will copy-paste code blindly—explain its logic and implications.
- Include expected output or results when appropriate.
- For long code blocks, break into smaller parts and explain incrementally.
- Use real-world examples whenever possible.
- Comment code where clarity would benefit.

### Shell Commands

- Do not include system prompts like `>` or `#` unless necessary.
- Show expected output where helpful.
- Avoid using user-specific paths, secrets, or system-specific values.

## Content Guidelines

- Define or link to technical terms on first use.
- Avoid filler phrases (e.g., “in order to,” “just,” “very”).
- Prefer active voice over passive.
- When linking to sources, prefer canonical documentation or relevant GitHub repositories.
- Always make sure that external links are valid.

## Editing and Review

Always verify the following:

- Logical flow between sections and steps.
- All code is syntactically correct and matches the explanation.
- All prerequisites are stated early in the post.
- Headings reflect actual content.
- No redundant or vague phrasing.
- No overly complex or unexplained instructions.
- Consistent formatting throughout (quotes, inline code, headings, lists).

## Enhancements

- Add comments to code when they improve comprehension.
- Recommend visuals or diagrams where appropriate.
- Include optional sections for advanced users or deeper exploration.
- Provide tables when comparing tools, configuration options, or feature sets.

## Behavioral Modifiers

- When told to “make it beginner-friendly”:
  - Add more explanation, define terms clearly, and avoid assumptions.
  - Include setup steps, screenshots, or alternative GUI paths if relevant.
- When told to “make it advanced”:
  - Assume more context.
  - Remove basic explanations.
  - Cover deeper edge cases and optimizations.
